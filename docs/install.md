# Installing a promoted stack

`pi-stack-install` installs one promoted, attested `stack/<sha>` release into your own Pi home. It does not need chezmoi, these dotfiles, Homebrew or a GitHub login. Code: `integration/harness/install.py`.

## Command

Pick a promoted SHA from the `stack/*` releases [here](https://github.com/nredd/pi-harness/releases), then run:

```sh
uvx --python 3.13 --exclude-newer 2026-10-23T00:00:00Z \
  --from 'git+https://github.com/nredd/pi-harness@<installer-sha>#subdirectory=integration' \
  pi-stack-install <stack-sha>
```

- `<stack-sha>` is the promoted commit you install.
- `<installer-sha>` must be an exact, published `main` commit containing the installer, never an unmerged PR or candidate SHA. Use the same SHA as `<stack-sha>` when that promotion contains `integration/harness/install.py`: then one pin covers both, and the installer passed the same promotion gates. `stack/24889f7896be7157bf9077a41465a3b29620879f` predates the installer, so for it use any `main` commit that has the installer.
- Add `--plan` to verify and print the plan without changing anything. Add `--yes` to agree to overwrites without a prompt.

Nothing is piped into a shell. `uv` fetches the pinned Git commit, so Git's object hashes bind the installer source to the SHA you typed. `uv` also initializes that commit's `forks/pi` submodule (the core source, unused by the installer) and caches the checkout, so the first run downloads more than it needs. `--python` and `--exclude-newer` fix the interpreter and resolve the installer's Python dependencies (pydantic) as of a fixed instant instead of the newest release.

## What it installs

- The core release named by the snapshot (`stack.core.tag`, e.g. `v1.3.0-nredd.8`) into `~/.local/share/pi-stack/core/<tag>/`, with the same npm steps as the Homebrew formula (`harness.release.fetch_release`). Homebrew is never used, so a newer formula cannot replace the pinned core.
- A `pi` link in `~/.local/bin` (`--bin-dir` changes it). Add that directory to `PATH` if it is not already.
- Every package source in the snapshot's order, through that core's own `pi install`, into `~/.pi/agent/npm`.
- In `~/.pi/agent/settings.json`: `packages` set to the snapshot's exact declarations (resource filters kept as written, so the preset loads only its footer extension), plus the snapshot's `settings` keys (`quietStartup`, `fullscreen`). Every other key you have is kept.
- In `~/.pi/agent/subagents.json`: `packageAgents: false` when a source is filtered, because pi-subagents loads package agents outside Pi's filters. Other keys are kept.
- Disabled extensions (`disabled_extensions`, currently `@nredd/pi-computer-use`) are installed without npm lifecycle scripts and declared with `extensions: []`, so they are never loaded and their native helper is never built or launched.

`PI_CODING_AGENT_DIR` and `XDG_DATA_HOME` move the agent and installer directories as they move Pi's. `PI_CODING_AGENT_DIR` gets Pi's own tilde rule: a leading `~` or `~/` means your home directory, and nothing else is expanded (not `~user`, not `$VAR`). Pi also accepts a `file://` URL there; the installer refuses one (exit `2`, nothing changed) rather than reimplement Node's `fileURLToPath`, so set the plain path. `XDG_DATA_HOME` is used only when it is absolute. Empty or relative values (including `~/...`, which XDG does not expand) are ignored, as the XDG spec requires, falling back to `~/.local/share`. This is the only `XDG_*` variable the installer reads.

## What you configure yourself

The installer never reads, copies or writes credentials or personal state. After installing:

- Log in: run `pi`, then `/login`, or set your own provider API keys.
- Choose default and enabled models and any router profiles.
- Add memory, MCP servers, personal prompts, skills or themes if you want them.
- `@nredd/pi-computer-use` stays off on both platforms, disabled by installer policy. Its macOS helper needs Screen Recording and Accessibility (TCC) permissions you grant yourself; opt-in Linux setup is documented [here](../packages/computer-use/docs/linux.md).

`auth.json`, `models.json`, sessions, memory and every other file in the agent directory are never touched. Machine-specific configuration (dotfiles, enterprise overlays) stays out of the snapshot by design.

## Threat model

The installer defends against accidental layouts, partial installs and interrupted runs. Installer-owned
switch and recovery mutations anchor every directory component from `/` through the backup, agent,
link, core, journal and state parents with `O_NOFOLLOW | O_DIRECTORY`. Renames use held descriptors
for BOTH operands; atomic file creation/replacement, symlink creation, deletion and lock creation use
held parents too. A parent renamed or substituted after admission cannot redirect those mutations
into the substitute. Identity checks refuse further progress and retain the journal on a detected swap;
a rename already in flight can have completed in the original, renamed directory. Restore the directory
namespace manually before retrying. Explicit symlinked roots remain supported: layout resolution
canonicalizes them before anchoring, rather than rejecting the user's chosen storage location.

This is pathname-redirection hardening, NOT a same-UID sandbox or protection from arbitrary host
compromise. That user can edit the installer, its files and the final entries directly, and package
subprocesses retain ordinary same-user filesystem access. Content verification immediately before a
restore rename does not isolate a leaf from a later concurrent edit. A pending `record()` whose backup
is absent is skipped only if the live original's device, inode and ctime still match. Otherwise recovery
fails loudly and keeps the journal for manual cleanup; legacy journals have no pending identity.
A crash between recording intent and saving an original is not a promise of automatic recovery.

Mutation/source-guard coverage:

| Caller | Held source and destination parents |
| --- | --- |
| `locked`, `apply` | Pin existing root/agent/bin/core/backup ancestors before planning/staging; create absent tails only when needed. Lock, staging-directory creation and empty backup-directory removal use parent descriptors. |
| `Journal.record` / `save` | Retain the live parent across write-ahead intent and move `live.name` into the held per-run backup directory. Both rename operands are descriptor-relative. |
| `stage`, `install_packages`, `Journal.place` | Hold the per-run staging directory and staged agent directory from creation through verification and switch. A source-parent substitution after verification refuses before switch. Hash replacement identities and rename using the same held source parent; the core's source parent is the per-run staging directory. |
| `switch_anchored`, `replace_file`, `write_atomic` | Hold live agent/bin/core/state/journal parents through mkdir, symlink, exclusive temporary creation, replace and temporary cleanup. Atomic writers outside a transaction own a short-lived descriptor scope. |
| `rollback`, `rename_restore`, `finish_aside` | Hold backup and live parents through restore preflight, reversible target/aside renames, backup restoration, verified aside deletion, progress rewrites and journal unlink. Recursive deletion uses the standard library's descriptor-relative, symlink-resistant `rmtree`. |
| `Journal.commit`, `run_preflighted` | Validate held directory identities before journal removal; stale staging cleanup uses the lock's held installer parent. |

Scratch downloads in the independent verification temporary directory and `fetch_release`/npm/Pi
subprocess internals are not descriptor-relative installer transactions. Staging checks its held source
parents before/after those operations and refuses switch on a detected substitution, but cannot prevent
a subprocess from writing through a substituted pathname during execution. Nor does parent anchoring
freeze final files/trees or defend against new real entries deliberately moved into an authorized tree.
Those are ordinary same-user code/filesystem privileges, not a sandbox supplied by this change.

## Verification, before any change

1. Platform and prerequisites, all reported at once.
2. `stack-snapshot.json` is downloaded from the `stack/<stack-sha>` release. Its attestation bundle comes from GitHub's public attestations API (no token), and `gh attestation verify --bundle` must accept it for repository `nredd/pi-harness`, signer workflow `nredd/pi-harness/.github/workflows/promote-stack.yml`, source ref `refs/heads/main`, hosted runners only. These are the consumer requirements in [stack promotion](stack-promotion.md#consumer-requirements). GitHub limits anonymous API use to 60 requests an hour per IP address; when that refuses the lookup, `gh attestation verify` is retried without `--bundle`, so `gh` fetches the attestation with its own login (`gh auth login` or `GH_TOKEN`). The installer never reads a token; without a login the rate limit is a verification failure. A `GH_TOKEN` in your environment is necessarily inherited by `uvx`, `uv`, the Git that fetches the installer, and the installer process (none of which use it). The installer passes GitHub token variables (`GH_TOKEN`, `GITHUB_TOKEN` and their enterprise forms) only to `gh attestation verify` when it must fetch without a bundle, and strips them from every other child: `gh` with a local bundle, `node`, `npm`, `pi install` and the `pi --version` check.
3. The bytes are validated with `StackSnapshot` (schema, canonical `stack_sha256`) and `source_sha` must equal `<stack-sha>`. No other interpretation of the manifest exists: the installer reuses `harness.promotion` and `harness.stack`.
4. The core release identity is checked with `validate_release_identity`; each recorded asset is hashed, and attested by `nredd/pi`'s `fork-release.yml` for non-legacy tags. Legacy tags `v1.3.0-nredd.3` to `.7` predate that workflow and rely on the frozen digests in `harness/release.py`. The snapshot must record both installed tarballs (`pi-coding-agent`, `pi-tui`), and staging downloads the core again, so those bytes are checked against the snapshot's digests (`harness.release.verify_asset`), never a re-read `SHA256SUMS`. `v1.3.0-nredd.8` is the first non-legacy core release (`fork-release.yml` run [40929216888](https://github.com/nredd/pi/actions/runs/40929216888)), so installer acceptance on a snapshot selecting it exercises the real `SHA256SUMS` plus provenance path (`nredd/pi`, `fork-release.yml`, `refs/tags/<tag>`, hosted runners only); older snapshots still exercise the frozen-digest path.
5. The digest-verified core tarball's `package.json` must be an object naming `@earendil-works/pi-coding-agent`, with a numeric major.minor.patch `version`, a `bin` object containing a nonempty `pi` CLI path, and an `engines` object containing a supported string `node` range. Malformed fields fail verification (exit `3`) with the field requirement, not a traceback. Node.js must satisfy that `engines.node` range (`>=22.19.0` for `v1.3.0-nredd.8`).

Only `npm:<name>@<exact-version>` registry pins (scoped or unscoped), tagged `git:github.com/...@v...` sources and explicit local directory paths are valid stack sources. npm aliases (`alias@npm:real@version`, including a leading Pi `npm:` prefix), `git+` URLs, `file:` specs and tarball URLs are not supported and fail stack validation before installation. An alias's installed manifest and lock entry legitimately name the real package, not its `node_modules` alias; they must not be interpreted as ordinary registry pins. Git repository and local directory names do not pin a manifest name: those manifests need nonempty string `name` and `version` fields, but are not compared with the repository/path.

After staging, each installed npm package name and version must equal its pin, and each owned `@nredd/` package's npm lockfile integrity must equal the SHA-512 the promotion verified. Shape or identity errors name the offending manifest `name`/`version` or lockfile `root`/`packages`/`version`/`integrity` field; live mismatches require repair with consent rather than a traceback. Third-party packages are pinned to exact versions and fetched from `registry.npmjs.org` with an empty npm config; their tarballs are not independently attested. Transitive dependencies (of the core and of every package) are NOT pinned by the snapshot: npm resolves them from the registry at install time within each package's declared ranges, so two installs of one SHA can differ below the pinned top-level versions.

A failed check exits before anything in your home changes. Snapshot downloads, release checksums, non-legacy core assets and attestation bundles share HTTP read error handling: truncated bodies, HTTP protocol failures, I/O errors, timeouts, TLS failures and malformed response lengths become verification failures (exit `3`) naming the URL host and reason, not tracebacks. Download diagnostics have the stable form `Could not fetch '<url>': <reason>`, with the requested URL exactly once per diagnostic. HTTP failures use status plus reason, e.g. `HTTP 404 Not Found`, `HTTP 403 Forbidden` or `HTTP 500 Internal Server Error`, never urllib's `HTTP Error ...` representation. DNS failures say `DNS lookup failed`; timeouts say `Request timed out`; truncated responses say `Incomplete response: received N bytes, expected M more` (the last clause is omitted when the missing count is unknown). The CLI prefixes verification failures with `VERIFICATION FAILED, nothing changed: ` and exits `3`. Higher-level snapshot, checksum, asset and attestation callers preserve that normalized download diagnostic rather than repeating the URL in another download/fetch wrapper. Attestation rate-limit status is retained for the gh fallback.

Every URL and redirect must use HTTPS. Public downloads accept only URL strings or requests with an `Accept` header; all other caller headers are refused before any network access, so redirects cannot forward caller credentials. A present `Content-Length` must be a single non-negative decimal integer and match the received bytes; responses with or without that header are capped at 256 MiB.

## Child environment

Every external process (`node`, `gh`, `npm`, `pi`, and release Git lookup) receives an explicit environment through one helper. Only these parent keys are inherited when present: `HOME`, `PATH`, `LANG`, `LC_ALL`, `TMPDIR`, `TERM`, `XDG_DATA_HOME`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME`, `XDG_RUNTIME_DIR`, `CI` and `GITHUB_ACTIONS`. `PATH` is made absolute and frozen as described below; staging replaces `HOME` with its private home. Release Git lookup uses an isolated home/config and disables system Git config and prompts.

Connectivity-only parent keys also reach EVERY child, including `npm`, `gh`, `node` and `pi`, to support enterprise proxies and CAs. Names are exact and case-sensitive:

- `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`, `ALL_PROXY`, `http_proxy`, `https_proxy`, `no_proxy`, `all_proxy`: proxy routing and bypass lists. Credentials in proxy URLs reach the child unchanged.
- `SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE`, `CURL_CA_BUNDLE`: absolute existing CA files only.
- `SSL_CERT_DIR`: an absolute existing CA directory only.

Connectivity values containing NUL, LF or CR are dropped. Relative, missing or wrong-kind CA paths are dropped too. Each drop emits a one-line warning naming ONLY the variable and reason, never its value. Paths are not expanded (no `~` or `$VAR` expansion). The helper preserves valid values verbatim; these settings configure transport, not package sources. CA paths are resolved before existence/type checks; the original absolute spelling is passed unchanged to children. The same validation and value-free warnings apply to the installer's own downloads. Trusting an enterprise CA is the operator's choice.

Installer diagnostics redact proxy URL userinfo (`user:pass@host` -> `host`), including child output echoed in exceptions, environment dumps and version messages. Redaction runs before output-tail truncation. A linear delimiter/authority scanner consumes through the authority's FINAL `@`, so a decoded password containing `@` cannot leave a suffix behind without quadratic regex retries. Known configured proxies are matched in both encoded and percent-decoded form, with or without their scheme, including decoded `:`, `/`, `%`, Unicode and IPv6 hosts. Known `user:password` pairs are masked as `[redacted]` even without a host or with only a trailing `@`. Username-only strings are not treated as standalone secrets. Scheme-less authority/userinfo matching remains boundary-aware; password masking is deliberately not.

Decision: redact EVERY occurrence of each nonempty configured proxy password, including literal, percent-decoded and percent-encoded forms, regardless of length or word boundaries. Each raw/decoded password also contributes its NFC and NFD canonical-equivalent literal and percent-encoded forms; compatibility normalization (NFKC/NFKD) is not applied. Percent-escape hex case is normalized in both matching forms and returned diagnostic text, including unrelated escapes, so lowercase and mixed-case escapes cannot bypass masking; ordinary letter case is unchanged. Very short passwords may over-redact unrelated text. Empty passwords are skipped; username-only userinfo is handled as before. Arbitrary transformations such as base64 are not promised. Raw child environments are never logged by the installer.

Password replacement uses at most 96 literal passes (raw/decoded x original/NFC/NFD x literal/percent-encoded for each of eight proxy keys), longest first. A one-character mask absent from every password's alphabet prevents output growth, replacement collisions and new secrets across a replacement boundary. If no safe mask character is available, or a potentially credential-bearing proxy value (`@` present) exceeds 8192 characters, the entire diagnostic is omitted rather than risk a leak or unbounded work; child connectivity values themselves are not changed. Large credential-free bypass/proxy lists do not trigger this cap. The URL scanner's character-search/read work is checked on 1 MiB and 4 MiB adversarial inputs, without wall-clock timing assumptions.

All child-error boundaries and their operation wrappers use `detached_exception`: the replacement keeps its domain type/metadata, while its complete underlying traceback goes through the single `format_exception_redacted` path into a sanitized cause. Callers raise it outside their exception handlers, so neither `__cause__` nor `__context__` retains the raw child exception. Release CLI exits also sanitize `SystemExit.code`, not only its message. This covers `node_version`, `install_packages`, `post_check`, release Git/npm/gh calls, snapshot/core provenance wrappers, core staging, kept-core checks, apply/rollback reporting and the healthy-no-op check. Standard `traceback.format_exception` and logging with `exc_info=True` see sanitized child/transport causes. This protects installer-generated diagnostics, not arbitrary child-written files.

The remaining explicit `from error` chains were audited: local filesystem/layout/lock/journal/consent/manifest/schema failures are not child errors; download/checksum/attestation-bundle wrappers chain the already-detached `FetchError` (or local decode/JSON failures). The named-cause inventory records every remaining site and its reason, and rejects new raw child wrappers. There are no raw `from exc`/`from e` child chains hidden outside that inventory.

All other parent variables are dropped by default, including `NODE_OPTIONS` (can execute a preload with `--require`/`--import`), `NODE_PATH` (changes module resolution), every `npm_config_*`/`NPM_CONFIG_*` variable (including registry/auth/prefix settings), every `PI_*` variable, `BASH_ENV`, `ENV`, `LD_PRELOAD`, `DYLD_INSERT_LIBRARIES`, `PYTHONPATH` and every `GIT_*` variable. A mirrored npm registry is deliberately out of scope: a registry override can redirect packages or their configuration can execute code. Digest checks would catch changed core bytes and a changed owned `@nredd/` top-level lockfile integrity, but NOT arbitrary third-party or transitive substitutions: those have no independent snapshot digest. The owned integrity check also runs AFTER package installation, not before lifecycle execution. Provenance is not a blanket defense for registry overrides.

The installer supplies its own npm config/cache/registry settings and disabled-package lifecycle flags, and its own Pi offline/update/telemetry flags. `pi install` gets the private staged `PI_CODING_AGENT_DIR`; the installed `pi --version` gets the installer-resolved live agent directory, never the parent's raw value. Only `gh`'s authenticated attestation fallback additionally receives `GH_CONFIG_DIR` and the four GitHub token variables (`GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`). A local-bundle verification gets none of those keys. This is environment filtering, not a sandbox or credential-capability isolation: same-user package code can still access the filesystem and inherited PATH shims described above.

### Installer fetch transport and proxy precedence

The installer's HTTPS downloads use an explicit urllib opener, not ambient/platform proxy discovery. The opener receives only the shared validator's connectivity values. It uses `HTTPS_PROXY`/`https_proxy`, falling back to `ALL_PROXY`/`all_proxy` only when neither HTTPS key is present; an explicitly empty HTTPS setting disables that fallback. `HTTP_PROXY` is retained for children but does not route HTTPS downloads. Installer proxies must use HTTP CONNECT (a bare proxy authority means HTTP). urllib cannot layer TLS to an HTTPS proxy; HTTPS-proxy and SOCKS URLs fail closed for installer fetches rather than sending credentials over a downgraded connection. Children retain their own support for those schemes. HTTP CONNECT proxy authentication itself is plaintext to the configured proxy; HTTPS protects the tunneled origin connection, not the proxy credentials on that hop.

For each `HTTP_PROXY`/`http_proxy`, `HTTPS_PROXY`/`https_proxy`, `ALL_PROXY`/`all_proxy`, `NO_PROXY`/`no_proxy` pair, differing valid values emit one value-free warning naming both variables. Children receive both original spellings unchanged. Installer fetches choose lowercase when present, even when empty. The explicit bypass list is matched by urllib's environment-only `proxy_bypass_environment`, never macOS/system proxy state: empty means no bypass, `*` bypasses every host, a `host:port` entry matches that port only, and a bare domain or leading-dot domain matches the domain and its subdomains. Entries are comma-separated. Ports in URLs participate in matching; urllib does not infer a missing port in a bypass entry. No bypass/proxy value appears in a warning.

TLS uses `ssl.create_default_context(cafile=..., capath=...)` with validated `SSL_CERT_FILE`/`SSL_CERT_DIR`, falling back to explicit compiled-in default CA paths. It never lets OpenSSL silently reread rejected ambient CA paths. Without an available explicit/default trust store, the hostname-verifying context fails closed. `NODE_EXTRA_CA_CERTS`, `REQUESTS_CA_BUNDLE` and `CURL_CA_BUNDLE` are loaded as additional CA files via `load_verify_locations`, in that order. An existing but malformed/unreadable bundle fails verification, rather than disabling TLS. We deliberately retain and honor the Requests/curl selectors for the installer's own fetches; native `node`, `npm` and `gh` do not consume those two selectors themselves.

Children keep their own transport semantics. Python urllib prefers lowercase; curl-family tools deliberately ignore uppercase `HTTP_PROXY`; Node/npm and Go-based `gh` choose proxies/bypass entries according to their own versions and libraries, not the installer's rules. `NODE_EXTRA_CA_CERTS` extends Node's CA store (including npm/Pi's Node processes), not Go's. `SSL_CERT_FILE`/`SSL_CERT_DIR` support depends on the child's TLS backend/platform and Node's OpenSSL/system-CA configuration. For `gh` on macOS, provision the enterprise CA in the system trust store when its Go TLS backend uses that store. Passing a setting is not a claim that every child implements it.

### Installer child scope

The install path spawns exactly `node_version`, `install_packages` and `post_check` in `install.py`, plus `verify_attestation` and `fetch_release` in `release.py`; `release.py` also has the shared release Git lookup `gitlink_tag`. Every subprocess call in those two modules uses `child_environment`, with no bypass exceptions. The AST inventory test enumerates all calls and requires the helper, including local `env` assignments.

`promotion.py.run_command`/`descends_from` are separate promotion CLI Git/build infrastructure, not installer children. The installer reaches promotion's read-only snapshot/core validation (`verify_core_assets`), whose downloads and provenance use the shared release helpers, not `run_command`. Other harness spawns in `sandbox.py` (`Sandbox.env`), `publish_gate`, `power`, `stats`, `rpc`, `git_fixture`, `tmux` and `headless` are test/benchmark/promotion infrastructure. They retain their separate environment policies and are NOT covered by the installer-child claim. `uvx`/Git that fetch the installer run before the installer starts and are outside its subprocess boundary too.

## Network trust

Independent of registry transport, the promoted snapshot is authenticated by its GitHub attestation and identity checks, core tarball bytes are checked against the authenticated snapshot's SHA-256 (plus non-legacy provenance), and the snapshot records independently verified expected SHA-512 digests for owned `@nredd/` top-level packages. The owned check compares npm's installed lockfile integrity AFTER installation; it is not a pre-lifecycle complete byte audit or a sandbox for lifecycle code.

Third-party top-level packages have exact version pins but NO independently authenticated integrity in the current `StackSnapshot`. Third-party and core/package transitive dependency integrity in the generated npm lockfile comes from the same registry transport as their tarballs; that lockfile is not a separately authenticated promotion lock. The root development `package-lock.json` does not pin the installer's runtime dependency graph.

A hostile proxy plus a user-configured trusted replacement CA can replace registry metadata/tarballs for third-party and transitive dependencies. Those bytes rely on registry transport trust, equivalent to `npm install` behind the same proxy, NOT mandatory provenance for every dependency. The operator already trusts that CA for traffic it can intercept; accepting it does not extend snapshot/core/owned provenance to third-party bytes. Track independent byte authentication [here](https://github.com/nredd/pi-harness/issues/169).

## Prerequisites and platforms

- `uv` (to run the command), Git (for `uv` to fetch the pinned commit), `gh` (GitHub CLI with `gh attestation verify`; no login unless the anonymous rate limit is hit), Node.js meeting the core's engine, npm.
- Network access to `github.com`, `api.github.com`, the Sigstore TUF CDN that `gh` uses, and `registry.npmjs.org`.

The installer root must be a directory or absent. A regular file at that path, or a creation failure such as `EACCES`, `ENOSPC` or `EROFS`, is a clean environment/layout refusal (exit `2`, installed state unchanged).

The installer directory (`XDG_DATA_HOME`), the agent directory (`PI_CODING_AGENT_DIR`) and the link directory (`--bin-dir`) must be on one filesystem, including the installer directory's own `staging`, `backups` and `core` subdirectories if you mounted any of them separately: the switch-over renames staged trees and backups between them. Otherwise the run exits `2` before anything changes.

Supported, because the real installer acceptance runs there: macOS on Apple silicon (`Darwin/arm64`) and Linux x86-64 (`Linux/x86_64`). Everything else, including Windows, WSL, Linux ARM64 and Intel macOS, is refused up front rather than guessed. WSL reports `Linux/x86_64`, so central admission detects it physically (`harness.paths.is_wsl`, `/proc/version`) before layout or journal access, including pending `--plan` reporting and `--yes` recovery. There is no CLI bypass. On supported platforms, restoring an interrupted switch's journal (below) needs no network or external tools and still runs first. Every mode checks the platform and required Unix primitives (`fcntl`, no-follow/directory/nonblocking flags, ownership and permission APIs) before layout resolution or any journal access. Native Windows is refused cleanly (exit `2`, nothing changed), including pending-journal reporting with `--plan` and recovery with `--yes`; removing Unix-only APIs cannot bypass admission.

Each tool is run from the absolute path `PATH` found it at, never from what a link there resolves to: version managers such as Volta or mise link `node` to one dispatcher that picks the runtime by its own name. Preflight's absolute `node`, `npm` and `gh` paths are retained through verification and staging. Every child's `PATH` entry (including empty entries) is made absolute relative to the preflight working directory before staging changes cwd, and the directory of the validated `node` is prepended. Thus npm's `#!/usr/bin/env node` or `#!/usr/bin/env -S node` shebang uses the same Node dispatcher preflight validated, even if another Node appears earlier in the original PATH. Symlink dispatchers are retained without resolving their targets; the parent process environment is not changed.

## Existing installations and consent

The installer prints the plan first: the packages in order with their filters, each `CREATE`, and each `OVERWRITE`. A nonempty plan explicitly declares creation of `installed.json` when absent, plus each absent permanent parent directory it needs (exact mkdir paths, not permission to write arbitrary descendants). Directory existence is captured before acquiring the lock, so mkdirs performed by lock acquisition remain declared in both `--plan` and normal-run CREATE output. Existing symlinked installer roots are resolved to their directory target before this capture. The named `lock` file is transaction scratch used only for serialization, not an installed payload, so it is exempt from permanent CREATE declarations; its permanent parent directories are not exempt. Creating things in a clean home needs no confirmation. Anything that replaces existing state needs consent: answer `y` at the prompt, or pass `--yes`. Without a terminal and without `--yes`, it exits `4` and changes nothing. EOF while answering either an overwrite or recovery prompt is declined consent too (exit `4`, nothing changed), not an uncaught `EOFError`.

Overwrites include the existing `installed.json` state record whenever a nonempty plan will replace it, an existing core prefix when reinstalled, existing `~/.pi/agent/npm` and `~/.pi/agent/git` trees (both are replaced and backed up, even when the stack installs no git package), changed `settings.json` keys, packages you declared that are not in the stack (they stop loading), `subagents.json`, and an existing `~/.local/bin/pi`. Everything replaced is moved or copied to `~/.local/share/pi-stack/backups/<UTC time>-<sha>/` first and kept.

Every path is classified with `lstat` before it is opened, so a FIFO, socket or device is refused instead of read (a FIFO would block the run forever). Accepted kinds, per path:

- `settings.json`, `subagents.json`: a regular file, or a link to one, which is read through. A link that would change is refused (exit `1`): an atomic replace would turn your link into a regular file. A dangling link counts as absent, so it is refused the same way when the plan writes the file. Any other kind, including a link to one, exits `2`.
- `installed.json`: a regular file only. A link is never followed and, like any other kind, exits `2`.
- `~/.pi/agent/npm`, `~/.pi/agent/git`: a directory or a link.
- `~/.local/bin/pi`: a regular file or a link.
- Installed `package.json` manifests: regular files or links to regular files, read nonblocking and checked again after opening. A missing, invalid or special manifest makes the package set require repair, never a blocking read.
- `core/<tag>`: a directory or a link, backed up when replaced. Other kinds exit `2` before staging.
- `backups` (the store under the installer directory): a real directory, or absent. A link or any other kind exits `2` before the prompt and before anything changes. The switch opens the store and its per-run directory with `O_NOFOLLOW | O_DIRECTORY`; backup renames are relative to the held directory descriptor, never a later symlink lookup. Directory identities are checked during the switch and before commit. A store swapped after the final pre-switch check is refused; a later swap cannot redirect backup writes, and a failed recovery keeps its journal.
- `lock`: an owned regular file, not writable by group or others. Links and special files exit `2`; opening is nonblocking, never follows a final link and never truncates existing bytes. The opened descriptor is checked before `flock`. A lock left group-writable by an earlier build running under `umask 002` is refused the same way (exit `2`, nothing changed): run `chmod g-w ~/.local/share/pi-stack/lock` once, then rerun. The installer never loosens or rewrites a lock itself.
- `transaction.json`: see the journal below.

A corrupt `settings.json` or `subagents.json` stops the run (exit `1`); fix or move it yourself. Refusals by kind happen before the prompt and before anything changes; move the entry aside yourself. A path that turns into a refused kind after planning is refused before it is journaled: the switch fails, rolls back the steps it already took and exits `1`.

## Reruns, updates, interruptions

- Rerunning the same SHA re-verifies the snapshot and finds nothing to change. It still runs `pi --version` through the link: an install that matches but does not run exits `1` instead of reporting `Already installed`, and changes nothing. A core prefix whose `pi-stack-core.json` marker matches the snapshot is never reinstalled, so when `pi --version` fails with that core kept (here, or after a switch that left it in place), the error names `~/.local/share/pi-stack/core/<tag>`: if it is damaged, remove it and rerun to reinstall it. Otherwise it exits `0`. Drift (a changed package version, a package manifest or npm lockfile entry that is missing or malformed, a removed link, an edited `packages` list) is planned and repaired, with consent for overwrites.
- Update or roll back by running the command with another promoted SHA. There is no moving pointer and no `latest`. Do not use `pi update` or `pi install` for the managed packages: the next installer run puts the snapshot's declarations back.
- During switch-over, originals (including settings files) are renamed into the anchored backup directory before replacements land. The multi-path switch is not atomic: an interruption between those operations can leave a target absent until the next consented journal recovery. Rename preserves the original entry's metadata and uses the same descriptor-relative primitive for files, links and trees.
- Everything is staged under `~/.local/share/pi-stack/staging/` first. A failure or interruption while staging leaves your home as it was. The replacement core stays in staging while packages install, so a live link to an existing core remains untouched on staging failure. The core moves into `core/<tag>` only during the journaled switch; any old prefix is backed up first.
- The switch-over is journaled in `~/.local/share/pi-stack/transaction.json` before each step. A failure during the switch, or a `pi --version` through the new link that does not run (checked before the journal commits), rolls back immediately. If the process is killed mid-switch, the next run restores every journaled step (after consent) first, offline: the restore needs no network, no prerequisites and no snapshot, so it completes even if verification then fails. The journal is created owner-only (`0600`) before any data is written, whatever your umask. It is trusted only if it is a regular file you own with no group or other permission bits (`0600`, or `0400` if you made it read-only) and every step names a path a switch replaces (`npm`/`git` trees, `settings.json`, `subagents.json`, the `pi` link, `installed.json`, exact versioned `core/<tag>` prefixes) with its backup, of the kind that path holds, inside one `backups/<run>/` directory; anything else fails closed before a single file changes. The journal names the exact paths of the run that wrote it, so restore with that run's `--bin-dir` and `PI_CODING_AGENT_DIR` (and `XDG_DATA_HOME`, which locates the journal); with other ones the steps fall outside the allowed paths and the run fails closed, saying so. A dangling `npm`/`git` tree or core link counts as existing state, so replacing it needs consent. `--plan` lists the pending `RESTORE` steps, exits `0`, and plans nothing until the restore has run. If a restore itself fails, the run says so and keeps the journal. At switch time, the installer records each prepared replacement's content identity BEFORE renaming it into place (or records intended absence). Recovery preflights every step before changing anything: live content must be absent, match that recorded replacement, or match the original. Post-crash edits or other kinds fail loudly without changing any entry, naming the path and a `mv -i` command to preserve it manually before retrying. Older journals without a replacement identity treat it as unknown and refuse unless live is absent or matches the original. Before each backup-to-live restore rename, an atomic journal rewrite records `restoring` intent with the backup path and a content identity: kind, SHA-256, device/inode, mtime and size. Regular files are hashed with streaming reads. Symlinks hash the raw readlink target without following it. A directory hashes sorted children recursively, each encoded as three unsigned big-endian eight-byte-length-prefixed fields: raw filename bytes, entry kind and lowercase hex content digest. File/link contents and names share an 8 GiB read budget per identity; trees are limited to 100,000 entries (including the root) and depth 128. Exceeding a bound or encountering a special file fails loudly and retains the journal. A retry redoes the rename if the backup remains and matches the recorded identity. Before any mutation, recovery compares the backup's device with the live entry and target parent; different filesystems fail loudly. Immediately before renaming, recovery opens regular files/directories once with `O_NOFOLLOW`, hashes through that descriptor, and checks the backup against the recorded identity; a mismatch preserves both live and backup entries. Existing live entries are renamed to a journaled sibling `.NAME.pi-stack-restore-<id>` first, NEVER deleted before restoring the backup. If the backup rename fails, the sibling is renamed back; it is deleted only after the original is safely live. An interruption with the sibling still present is reconciled using its recorded path and content identity on retry. Before removing the sibling, recovery verifies the restored live original against its recorded identity and atomically journals the sibling as `cleaning`. Before entering `cleaning`, recovery also records a bounded manifest of every aside entry: relative path, kind, size, SHA-256 and rename-stable identity fields. A retry verifies the live original again and hashes the remaining aside without following links. Removal is allowed only for absence, the recorded entry, or a verified partial tree remnant: every remaining path must occur in the manifest, directories must retain kind/device/inode, and files/links must retain their complete recorded identities. New content or a recreated aside refuses before any transaction mutation and retains the journal. Legacy `cleaning` metadata without a manifest refuses an existing aside for manual recovery. Manifest hashing has the same byte/entry/depth bounds as restore hashing; serialization must also fit the 1 MiB journal limit before deletion starts. A large npm tree can exceed that smaller serialized limit even though hashing succeeds. Recovery then retains the intact aside and journal, with the original safely live; automatic retries cannot finish until you preserve or remove that aside manually after verifying the restored original. This is a fail-closed manual-recovery limit, not a promise that every tree within the hashing bounds can be cleaned automatically. If the backup is missing, only a live target matching the SHA-256 AND every recorded identity field means the rename completed, so recovery records that progress without deleting the target. A missing backup with a nonmatching live target fails loudly and keeps the journal. Each completed restore is atomically recorded with the restored entry's device, inode and ctime (or absence for a newly created target), retaining its content identity when present, so retries skip it only while all recorded state still matches. Older `restoring` records containing only mtime/size cannot prove content identity and now fail closed for manual recovery; pending/saved/legacy and completed journals without `restoring` metadata retain their original-identity validation, but incomplete legacy steps also apply the unknown-replacement refusal. This covers process interruptions during rollback and anchors installer-owned mutation parents, not power-loss durability (see tracked follow-ups). Once all restores finish, an empty step list durably marks rollback complete before journal cleanup; a failed unlink is retried without requiring consumed backups. Originals not yet restored remain in `backups/`. New backup entries are first persisted as `pending` with the original entry's device, inode and ctime; a successful rename marks them saved. Before deleting any live target, recovery checks every expected backup. Without `restoring` intent, a missing backup is skipped only for a pending step whose live original still matches all three identity fields: the rename never started, so a failed or interrupted switch can roll back cleanly and remove the journal. Missing saved or legacy backups without matching `restoring` intent or recorded restore progress, or pending backups whose live original is absent or changed, still fail loudly and retain the journal for manual recovery. Pending metadata is strictly validated; this is interrupted-operation reconciliation, not isolation from arbitrary same-user edits.
- Journals are capped at 1 MiB before parsing. Oversized, deeply nested or allocation-failing JSON is untrusted (exit `1`, nothing restored) on both recovery and pending `--plan` paths; other untrusted journals also make pending `--plan` exit `1` rather than report a successful plan. All validation I/O errors, including unsearchable backup parents, become `RollbackError` refusals with the journal retained, never raw permission tracebacks.
- Only one installer runs at a time (`~/.local/share/pi-stack/lock`).

### Recovery transition table

The table is the expected transition oracle for the table-driven state-matrix test. Each row crosses all six live states. `original` means the recorded original identity still matches; `new` is the switch's recorded replacement identity; `other` includes post-crash edits and same-size, preserved-mtime content changes. Pending/saved/restoring rows have a recorded replacement; the legacy row represents a journal without one. Completed rows validate the recorded original or absence instead. Unknown replacements refuse unless the live path is absent or matches the original. Directory/symlink columns are different kinds from this matrix's original regular file. `restore` replaces the live entry with the verified original backup; `skip` records already-completed/never-started progress without changing the live entry; `refuse` retains the journal and all entries unchanged. A completed new target records absence and references no backup: a leftover backup-store file is unreferenced and must stay untouched. Existing backups in `restoring` rows must match the recorded content identity; mismatches always refuse, regardless of live state. Metadata must validate before any transition. Completed restores with content metadata check that too. Retries of a successful row are no-ops.

Exit codes: `0` installed or already installed, `1` failed (state unchanged or restored, as reported), `2` malformed stack SHA or arguments (usage), unsupported platform, split filesystems, an existing entry of a refused kind, an installer-root creation failure (installed state unchanged) or missing prerequisite, `3` verification failed, `4` consent required or declined.

To uninstall: remove `~/.local/bin/pi`, `~/.local/share/pi-stack`, `~/.pi/agent/npm`, and the `packages` key of `~/.pi/agent/settings.json`, or restore from `backups/`.

## Testing

Acceptance's installer-owned text anchors are stable contracts: missing prerequisites name each `` `<tool>` not found ``, plans use `CREATE`/`OVERWRITE` and name dropped sources, staging logs `pi install '<source>'`, and a healthy no-op rerun says `Already installed`. Unit tests exercise those message producers and exact network/CLI diagnostics. Version numbers and `pi list`'s `(filtered)` entries come from the pinned core itself, checked by the real acceptance and package-declaration units, not fabricated installer output.

- Deterministic ancestor-swap regressions: `integration/tests/test_install_ancestors.py`, including swaps between `record()`/`save()` and at the actual restore and atomic-replace syscalls. These are disposable POSIX fixtures, not fuzzing or live-install checks.
- Units, offline, against the real `stack/24889f7` snapshot bytes (the login-interoperability regressions require `gh`; they run only `gh auth token` against synthetic `hosts.yml`, never a network login): `integration/tests/test_install.py` (part of `make check-integration`).
- Real acceptance, in throwaway HOMEs with real GitHub, `gh`, npm and core: `make -C integration installer INSTALLER_SPEC='git+https://github.com/nredd/pi-harness@<installer-sha>#subdirectory=integration' STACK_SHA=<stack-sha>`. It covers missing prerequisites, an unpromoted SHA, tampered bytes and foreign signer/ref against real `gh`, a fresh install compared with the snapshot (order, filtered preset, disabled computer-use, owned integrity, `pi --version`, `pi list`), a no-op rerun, consent with an existing setup whose credentials and unrelated settings survive, and a SIGKILL during staging followed by a successful rerun. The staging marker wait has a 1200-second deadline and one-MiB output limit; success, EOF and timeout all kill the child process group and reap its leader. Cleanup has a separate 60-second deadline and checks for live group members with `/bin/ps`, repeating SIGKILL when a concurrent fork survives the first signal. It keeps the leader unreaped as the process-group ownership anchor until signalling finishes, then reaps it within the remaining deadline. It fails closed if a live member remains, so the rerun cannot delete staging under an orphaned npm writer; unreaped zombies cannot write and do not block it. macOS answers `EPERM` to a signal sent at a group that holds only zombies; that is accepted only when `/bin/ps` shows no live member, and `EPERM` with a live member still fails. A marker failure and cleanup failures are reported together, preserving the marker failure first. Offline subprocess coverage includes an externally supervised fork-at-signal writer that accepts a write request only after cleanup returns. The test leader and writers arm independent hard lifetimes before the marker and before blocking for requests, so regression failure cleanup never signals a potentially recycled PID/PGID. `.github/workflows/installer.yml` runs it on `ubuntu-24.04` and `macos-14` from the exact commit. Hosted runner IPs share GitHub's anonymous 60 requests/hour limit, so `main` pushes/dispatches and trusted same-repo pull requests (`head.repo.full_name == github.repository`) provision a temporary `gh` login using the read-only job token (`contents: read`, `attestations: read`, all other permissions disabled). A separate step pipes the token to `gh auth login`; acceptance uses a gh-only config shim. `make`/pytest receive only the nonsecret `INSTALLER_GH_CONFIG_DIR` path, not a token. Only the shim sets `GH_CONFIG_DIR` for `gh`; neither variable nor token reaches `uvx`, Git, package builds or other installer children. An always-running cleanup removes the temporary login. Fork pull requests and non-main dispatches remain anonymous and fail honestly when the limit refuses them. Same-repo authors are trusted, not fork-sandboxed. KNOWN RESIDUAL: package scripts still inherit the PATH shim and can use its login or read plaintext `hosts.yml`, even without token/config variables. No credential-capability isolation is claimed; see the trust assumption in [CI](ci.md).
